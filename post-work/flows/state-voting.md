FLOW: Voting State (Suspense Resolve → useOptimistic → Server Action → Auto-Revert)
ENTRY: `ExistingChatPage` starts `votesPromise = getCachedVotes(chatId, userId)` → renders `VotesProvider` + `VoteResolver` inside Suspense
STEPS:
  1. `ExistingChatPage` (server) → `getCachedVotes(chatId, userId)` with `'use cache'` + `cacheTag(cacheKeys.votes(chatId))` + `cacheLife('seconds')` → `getVotesByChatId(chatId, userId)` → returns `Vote[]`
  2. `getVotesPromise(chatId, session)` → if no user or guest, returns `Promise.resolve([])` → otherwise wraps with `.catch(() => [])` — vote fetch failure never propagates (graceful degradation)
  3. Page renders: `<VotesProvider chatId={chat.id}>` → initializes `serverVotes = useState<Vote[]>([])` (empty until VoteResolver resolves) → `useVotes(chatId, [])` → `useOptimistic([], reducer)` → `optimisticVotes = []` initially
  4. `VotesProvider` creates `VotesStore` via `createVotesStore()` (ref-stable) — module-level `voteByMessageId: Map<string, Vote>` with `subscribe/getVote/setVotes` pattern
  5. `useLayoutEffect([votes])` → `storeRef.current.setVotes(votes)` — syncs optimistic vote array into the Map-based store. On initial render, sets empty map.
  6. `<VoteResolver votesPromise={votesPromise}>` inside `<Suspense fallback={null}>` → `use(votesPromise)` suspends until promise resolves → chat renders immediately with empty votes, no blocking
  7. Promise resolves → `VoteResolver` renders → `useEffect` fires → `setServerVotes?.(resolvedVotes)` via `VotesSetterContext` → `VotesProvider.setServerVotes(resolvedVotes)` → `serverVotes` state updates
  8. `useVotes(chatId, serverVotes)` → `useOptimistic(serverVotes, reducer)` now has base state populated → `optimisticVotes = serverVotes` → `useLayoutEffect` → `store.setVotes(votes)` → `hasVoteMapChanged()` check → if votes differ from empty map → `voteByMessageId` updated → listeners notified
  9. `useVoteForMessage(messageId)` (per-message hook) → `useSyncExternalStore(store.subscribe, () => store.getVote(messageId), () => undefined)` → returns `{ vote, submitVote }` — only this message's vote, not the full array
  10. User clicks upvote → `submitVote(messageId, "up")` → `startTransition(async () => { ... })`
  11. Inside transition: `addOptimisticVote({ messageId, type: "up" })` → reducer: filters existing vote for message → appends new `Vote` with `isUpvoted: type === "up"` → `optimisticVotes` immediately reflects new vote → `useLayoutEffect` → `store.setVotes(optimisticVotes)` → `VoteButtons` re-renders with filled icon
  12. `await voteOnMessage({ chatId, messageId, type })` — Server Action call inside the transition → persists vote to database
  13. If success: transition settles → `serverVotes` is now stale but `useOptimistic` retains the optimistic value until the component re-renders with new base state (e.g., revalidation). Practically, the optimistic value matches what the server saved.
  14. If failure: `toast.error(result.error.message)` → transition settles → `useOptimistic` automatically reverts `optimisticVotes` to `serverVotes` (base state) → `store.setVotes(serverVotes)` → vote button reverts to previous state
  15. `VoteButtons` (memoized via `memo`) → custom comparator checks: `messageId`, `isAssistant`, `isLoading`, `vote?.isUpvoted`, `onVote` reference — skips re-render when only unrelated props change
  16. `hasVoteMapChanged(current, next)` → size check + per-entry `Object.is` comparison — prevents store notification when votes are structurally identical (e.g., same array passed twice)
BOTTLENECKS:
  - `useLayoutEffect` runs synchronously after ReactDOM mutations — `store.setVotes(votes)` fires during this phase, which means `useSyncExternalStore` subscriptions are triggered synchronously during layout. React handles this correctly (deferred re-render), but it's a tight scheduling window.
  - `hasVoteMapChanged` iterates ALL votes on every update — for chats with many messages/votes, this is O(n). Practically, most chats have <50 votes, so this is negligible.
  - The `VoteResolver` → `useEffect` → `setServerVotes` path introduces one extra render cycle after Suspense resolves — the Suspense boundary unblocks, VoteResolver renders, effect fires, state updates, then VotesProvider re-renders. Three renders from promise resolution to visible votes.
WASTE:
  - `useVotes` creates a new `Vote` object in the reducer with `userId: ""` — this is a placeholder that's never used for display. The vote is identified by `messageId`, and `userId` is only needed server-side. Creating objects with known-useless fields is minor waste.
  - `VotesProvider` always creates a `VotesStore` even for new chats with no messages — the store, Map, and listener Set are allocated but never used until votes exist.
  - The `EMPTY_VOTES_STORE` constant and `NOOP_SUBMIT` callback in `useVoteForMessage` handle the case where the hook is used outside `VotesProvider`. This is a defensive pattern — but if the component tree is well-structured, it should never be needed. The `NewChatPage` doesn't render `VotesProvider` at all, so vote buttons inside it would hit this path.
  - `useOptimistic` + `useTransition` pair — the transition wraps the entire server action call, meaning the transition is "pending" until the server responds. This blocks React from showing the optimistic state as "final" until the action settles. However, `useOptimistic` shows the optimistic value immediately regardless, so the transition pending state is only relevant for `isPending` consumers (which aren't used here — `[, startTransition]` discards the pending boolean).
SIMPLIFICATION OPPORTUNITIES:
  - The `VotesStore` (Map-based useSyncExternalStore) is an optimization to avoid re-rendering ALL vote buttons when ANY vote changes. Without it, the `useOptimistic` array would flow via context and every `VoteButtons` would re-render. The store-per-message pattern is correct and efficient — no simplification needed here.
  - `VoteResolver` could use `useInsertionEffect` instead of `useEffect` for earlier firing, or the `setServerVotes` could be called synchronously during render (since `use()` resolves during render). This would eliminate one render cycle.
  - The `VotesSetterContext` + `VotesContext` split follows the same pattern as `ChatStreamProvider` (separate read/write contexts). Consider whether a single context with stable ref-based dispatch would be simpler — the setter is only called once (from VoteResolver).
EXIT: Each `VoteButtons` instance receives per-message vote state via `useVoteForMessage(messageId)`. Votes are optimistic (immediate UI feedback), auto-revert on server failure, and stream in via Suspense without blocking the chat. Guest users see no vote buttons. The store-per-message pattern ensures only the affected vote button re-renders on vote action.
