## Deviations

**1. `ArtifactMetadata` and `ArtifactVersion` types omitted**

- **Plan said:** p00-scaffold.md P0-T06 action mentions "ArtifactMetadata, ArtifactVersion, Artifact (replaces old Document type)"
- **What was done:** Omitted these types. Only the types from the detailed `shared-types.md` §3 spec were created.
- **Why:** `shared-types.md` is the explicit "exact field definitions" source of truth (as directed by the task request). It defines `ArtifactStatus`, `ArtifactSuggestion`, and `UIArtifact` — not `ArtifactMetadata` or `ArtifactVersion`. The `Artifact` type already exists in `models.types.ts` (Drizzle-inferred) and each DB row IS a version (composite PK: id+createdAt). `ArtifactWithVersions` also exists in `models.types.ts`. Adding `ArtifactMetadata` (a Pick<>) and `ArtifactVersion` (an alias) would be premature abstractions with no current consumers.
- **Trade-offs:** If a future task needs metadata-without-content or explicit version typing, they can be added at that point with actual consumer requirements.

**2. `ChatStream` parameter renamed to `chatStream`**

- **Plan said:** shared-types.md §5 uses `ChatStream: ArtifactStreamWriter` (PascalCase parameter name)
- **What was done:** Used `chatStream` (camelCase) per project naming conventions
- **Why:** PascalCase for function/method parameters violates the project's naming convention (AGENTS.md, naming-conventions.md: parameters use camelCase). The redesign note "was streamWriter → ChatStream" appears to be a naming error.
- **Trade-offs:** Consumers referencing the spec's `ChatStream` name will need to use `chatStream` instead. Trivial rename.

## Findings

**1. `ArtifactSuggestion` is the canonical source**

`shared-types.md` §3 notes that `features/chat/types/chat.types.ts` §9 also defines this type and "should be replaced with a re-export from this file." When P3/P6 creates chat types, they must re-export from `@/lib/types/artifact.types` — not redefine.

**2. `ArtifactKind` import chain**

`artifact.types.ts` re-exports `ArtifactKind` from `models.types.ts`. `artifact-handler.types.ts` imports from `artifact.types.ts`. This means consumers can import `ArtifactKind` from either `models.types` or `artifact.types` — the artifact-context import path is preferred.
