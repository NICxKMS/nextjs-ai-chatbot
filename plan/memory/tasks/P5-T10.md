## Deviations

**patterns.md § 3 template vs actual data layer interface:**
The REST route template in `patterns.md` shows manual `limit + 1` over-fetching and slicing in the route handler. However, the actual `getChatsByUserId` in `lib/data/chat.ts` (P1-T06) already encapsulates this pagination logic internally — it accepts `PaginationParams { limit, cursor }` and returns `{ chats, hasMore, nextCursor }`. Duplicating that logic in the route handler would violate DRY and the data access pattern's encapsulation. The route handler delegates pagination entirely to the data layer.

- **Original design:** Route handler does `limit + 1` fetch, slices, computes `hasMore`/`nextCursor`
- **What was done:** Route handler passes clamped limit and cursor directly to `getChatsByUserId`, which handles pagination internally
- **Why better:** Avoids duplicating pagination logic already encapsulated in the data layer; follows single-responsibility
- **Trade-offs:** None — the response shape (`{ chats, hasMore, nextCursor }`) is identical
