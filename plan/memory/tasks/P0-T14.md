## Findings

- The Next.js 16 proxy docs (`.next-docs/01-app/03-api-reference/03-file-conventions/proxy.mdx`) confirm: `NextResponse.next({ request: { headers } })` makes mutated headers available to downstream route handlers (request-side), while `response.headers.set()` sets response headers visible to clients. The oldapp used `response.headers.set()` for device type (client-visible response header). This implementation sets `x-device-type` on request headers per the spec requirement so downstream route handlers/server components can read it.
- The proxy docs note that `proxy.ts` runtime defaults to Node.js and cannot be configured — the `runtime` config option is not available for proxy files. The architecture doc mentions "edge" but the actual Next.js 16 behavior runs on Node.js runtime. This is a non-breaking distinction since the API surface is identical.
