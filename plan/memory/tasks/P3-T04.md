## Deviations

**Success criteria says:** "ArtifactHandler type defines create/update/render interface"

**What was done:** Re-exported the existing `ArtifactHandler` type from `lib/types/artifact-handler.types.ts` (P0-T06) which defines `create` and `update` only — no `render` method.

**Why:** The `render` concern is client-side UI rendering (which React component to show for each artifact kind). It is architecturally distinct from the server-side `create`/`update` operations that return `Promise<string>`. Adding a React component reference to a server-side handler type would create an incorrect coupling. The old app (`oldapp/lib/artifacts/server.ts`) also had no render method on its `DocumentHandler` type — rendering was handled at the component layer. The render mapping will be addressed in P4 when artifact UI components are built, likely as a separate client-side registry or component map.

**Trade-offs:** If P4 needs a unified handler+renderer type, the `ArtifactHandler` type in `lib/types/artifact-handler.types.ts` can be extended at that point. Current design is correct for all known P3 consumers (tools in P3-T13).

## Findings

1. **Old app used array-based lookup** (`documentHandlersByArtifactKind: DocumentHandler[]`) with `.find()`. New implementation uses `Map<ArtifactKind, ArtifactHandler>` for O(1) dispatch — strictly better.

2. **Render concern for P4:** When P4 builds artifact UI components, it may need a client-side kind→component map. This should be a separate concern from the server-side handler registry, potentially in `features/artifacts/`. The `ArtifactHandler` type should remain server-focused.
