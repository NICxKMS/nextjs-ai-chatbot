## Summary

Created three Server Action files for login, register, and logout in `features/auth/actions/`. All actions validate input with Zod, use Supabase server-side auth, clear the `guest_token` cookie on success, and redirect (never throw). Also created a shared Supabase action client helper at `features/auth/lib/supabase-action.ts` to avoid duplicating the cookie-adapter boilerplate.

## Files Changed

- `features/auth/actions/login.ts` — **created** — `login(prevState, formData)` Server Action; validates with `loginSchema`, calls `signInWithPassword`, clears guest token, redirects to "/"
- `features/auth/actions/register.ts` — **created** — `register(prevState, formData)` Server Action; validates with `registerSchema`, calls `signUp`, creates DB user record via `createUser`, clears guest token, redirects to "/" (or "/login" if email confirmation pending)
- `features/auth/actions/logout.ts` — **created** — `logout()` Server Action; calls `signOut` (best effort), clears guest token, redirects to "/login". No prevState parameter (not used with `useActionState`).
- `features/auth/lib/supabase-action.ts` — **created** — Shared `createSupabaseActionClient()` helper; creates a Supabase server client with a write-capable cookie adapter (no try/catch in `setAll`, unlike the read-oriented client in `session.ts`)

## Deviations

### D1: Additional helper file `features/auth/lib/supabase-action.ts`

**Plan says:** Three output files: `login.ts`, `register.ts`, `logout.ts`. `features/auth/lib/` contains only `guest.ts`.

**What was done:** Created `features/auth/lib/supabase-action.ts` as a shared Supabase client factory for action context.

**Why:** All three action files need to create a Supabase server client with a write-capable cookie adapter. The existing `createSupabaseServerClient` in `lib/auth/session.ts` wraps `setAll` in try/catch (correct for read-only Server Component context, where cookie writes are silently ignored). Action context requires cookie writes to succeed (auth tokens are set/cleared). Rather than duplicating ~15 lines in 3 files (violating "No duplicate logic" from AGENTS.md) or modifying the session.ts function with mixed semantics, a small dedicated helper in the same feature directory is the cleanest solution.

**Trade-off:** One additional unplanned file. Minimal — the file is 35 lines, single-purpose, and naturally collocated.

### D2: Rate limiting not implemented

**Spec says:** "Per-action rate limiting applied to login, register, and logout Server Actions (e.g., login: 5/min, register: 3/min)."

**What was done:** No rate limiting applied.

**Why:** No rate limiting infrastructure exists in the codebase yet. Redis is designated for rate limiting (per architecture docs) but the rate limiting module has not been built. This is deferred to a future task that builds the rate limiting infrastructure.

**Trade-off:** Auth endpoints are unprotected from brute-force until rate limiting is implemented.

## Findings

### F1: Rate limiting infrastructure needed

The spec requires per-action rate limiting for login (5/min), register (3/min), and logout. This requires a rate limiting module (likely Redis-backed) that does not exist yet. A future task should implement `lib/rate-limit/` and wire it into these actions.

### F2: Guest data migration not handled

Per the phase plan's explicit deferral note (AU-V8), guest-to-auth data migration is out of scope. When a user logs in or registers, their guest data (chats, artifacts) remains under the guest user ID. If migration is committed in the future, it would be wired into the login and register actions after the redirect-on-success path.

### F3: Email confirmation flow in register

If the Supabase project has email confirmation enabled, `signUp` returns a user but no session. The register action handles this by redirecting to "/login" instead of "/". P2-T05 (auth form) or P2-T07 (auth pages) may want to display a "check your email" message in this scenario — the current action only redirects.

### F4: Logout is best-effort on Supabase signOut

The logout action proceeds with cookie cleanup and redirect even if `createSupabaseActionClient()` returns null (Supabase not configured). This ensures users can always "log out" (clear cookies) regardless of Supabase availability.
