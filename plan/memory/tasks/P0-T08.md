## Deviations

1. **Error codes are granular, not simple names.** Task summary listed simple codes (UNAUTHORIZED, NOT_FOUND, etc.) but the authoritative spec in `plan/scaffold/shared-types.md § 11` defines granular `type:surface:detail` codes (e.g., `unauthorized:auth:no_session`). Followed the spec as the canonical reference — factory methods provide the simple API surface while codes carry precise context for logging and error routing.

2. **Added `serviceUnavailable()` factory method.** Task request listed 6 factories (unauthorized, notFound, forbidden, badRequest, rateLimited, internal). The shared-types spec defines a 7th: `serviceUnavailable()` → `offline:api:service_unavailable` (503). Added for completeness since dependents (P1-T05 Route Handlers) will need it. This maps to the W2-EH-02 resolution for upstream 503 handling.

3. **Added `toResponse()` method.** Not explicitly listed in task request but defined in shared-types spec and required by architecture (Route Handlers use `AppError.toResponse()` per patterns.md). Returns `NextResponse` with JSON `{ code, message }` body.

4. **`details` typed as `unknown` instead of `Record<string, unknown>`.** Spec says `Record<string, unknown>`, task request says `unknown`. Used `unknown` for flexibility — callers can pass any serializable value; consumers narrow as needed. A `Record<string, unknown>` is assignable to `unknown` so no downstream breakage.

5. **No CONFLICT error code.** Task summary mentioned CONFLICT but no such code exists in the shared-types spec or architecture. Omitted per spec.
