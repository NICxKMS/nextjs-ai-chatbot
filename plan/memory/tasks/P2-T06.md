## Deviations

### Extra file: `supabase-browser.ts`
- **Plan said:** Only `session-provider.tsx` as output file
- **What was done:** Also created `features/auth/lib/supabase-browser.ts`
- **Why:** The SessionProvider needs a Supabase browser client to subscribe to `onAuthStateChange`. The oldapp had this in `oldapp/lib/auth/client.ts`. The new codebase had no browser client utility. Placing it in `features/auth/lib/` follows the feature collocation pattern and parallels the existing `features/auth/lib/supabase-action.ts` (server action client). This is a necessary dependency, not scope creep.
- **Trade-offs:** None — this is the minimal utility needed.

### No client-side session mutation
- **Plan said (old app):** Old `AuthProvider` directly mutated session state from `onAuthStateChange` callback with Supabase user data
- **What was done:** Instead of direct mutation, `router.refresh()` triggers a server-side re-render that passes the updated session prop down, which syncs via the `useEffect([initialSession])` dependency
- **Why:** This is the correct Next.js App Router pattern — the server is the single source of truth for session. Direct client-side mutation would create drift between server and client session state. The server already runs `getAppSession()` which normalizes the session shape correctly for both authenticated and guest users.

## Findings
- **P2-T08 integration:** Root layout will need to call `getAppSession()` and pass the session to `<SessionProvider session={session}>`. The component-wiring.md already documents this pattern.
- **Browser client reuse:** `features/auth/lib/supabase-browser.ts` can be used by any future client-side auth consumers (e.g., real-time channel subscriptions that need the browser client). It's not specific to the SessionProvider.
