## Deviations

**Spec said:** "Import db from lib/db/client.ts"

**What was done:** `lib/db/migrate.ts` creates its own dedicated `postgres` connection with `max: 1` instead of importing the shared `db` from `client.ts`.

**Why:** The migration runner is a standalone script (`tsx lib/db/migrate.ts`) that must:
1. Use a single sequential connection for migration safety (`max: 1`)
2. Cleanly close the connection and exit the process after completion
3. Not depend on the shared connection pool's lifecycle

The shared `db` in `client.ts` uses the default connection pool (no `max: 1`) and provides no way to close the connection for clean process exit. This matches the established pattern from `oldapp/lib/db/migrate.ts` and Drizzle's own documentation.

**Trade-offs:** Slightly more code (3 extra lines) vs. correct migration semantics and clean process exit.

---

**Spec said:** "Uses drizzle-kit/migrate"

**What was done:** Uses `drizzle-orm/postgres-js/migrator` (the correct runtime API for programmatic migrations with the postgres.js driver).

**Why:** `drizzle-kit` is the CLI tool; `drizzle-orm/postgres-js/migrator` is the runtime library for programmatic migration execution. The spec conflated the two. The CLI command `pnpm db:migrate` (which uses drizzle-kit) is already wired in `package.json`.
