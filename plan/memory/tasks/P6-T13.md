## Summary

Created `GET /api/health` endpoint that checks database (SELECT 1) and cache (Redis PING) connectivity with latency measurements. Returns JSON with overall status (`healthy` | `degraded` | `unhealthy`), individual check results, and timestamp. No auth required. Added `ping()` export to `lib/cache/client.ts` to support the Redis health check.

## Files Changed

- `app/api/health/route.ts` — created: GET handler with parallel DB + cache checks, latency measurement, status derivation
- `lib/cache/client.ts` — modified: added `ping()` export wrapping `client.ping()` with graceful degradation

## Deviations

- **Added `ping()` to `lib/cache/client.ts`**: The task spec listed only `app/api/health/route.ts` as an output file. However, the cache client module did not expose a `ping()` method, which is needed for Redis health checking. Rather than bypassing the cache abstraction layer and importing Redis directly (which would violate the architectural pattern), a minimal `ping()` function was added to the cache client following the exact same graceful-degradation pattern as existing exports (`get`, `set`, `del`, etc.). This is a better approach because it maintains the single point of Redis access and is consistent with the existing API surface.
- **Removed environment health check**: The old app included an environment variable check (`checkEnvironmentHealth`). This was omitted as the task spec only requires DB and cache checks, and missing env vars would cause the DB/cache checks to fail anyway, making it redundant.
