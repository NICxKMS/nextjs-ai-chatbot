## Summary

Created vote types/schema and the `voteOnMessage` Server Action. The action validates input with Zod, rejects guests, verifies chat ownership, checks message-belongs-to-chat (IDOR protection), applies per-user rate limiting (20 votes/min via Redis), upserts the vote via `lib/data/vote.ts`, and invalidates the vote cache. Returns `ActionResult<{ messageId: string; type: "up" | "down" }>` — never throws.

## Files Changed

- `features/voting/types/vote.types.ts` — created: `voteSchema` (chatId uuid, messageId uuid, type enum "up"|"down") and `VoteRequest` inferred type
- `features/voting/actions/vote.ts` — created: `voteOnMessage` Server Action with full auth → validate → authorize → rate-limit → execute → invalidate flow
- `lib/errors/codes.ts` — modified: added `not_found:vote:message_not_in_chat` (404) and `rate_limit:vote:too_many_requests` (429) error codes
- `lib/cache/keys.ts` — modified: added `rateLimitVote` key builder for vote-specific rate limiting

## Deviations

1. **Added error codes to `lib/errors/codes.ts`**: The task spec didn't explicitly mention adding new error codes, but the IDOR protection requirement (`not_found:vote:message_not_in_chat`) and per-action rate limiting (`rate_limit:vote:too_many_requests`) needed dedicated codes within the strict typed ErrorCode system. Using generic codes would have been semantically incorrect and harder to debug.
2. **Added `rateLimitVote` key to `lib/cache/keys.ts`**: Per-action rate limiting required a dedicated Redis key builder to avoid collision with the general `rateLimit` key. This follows the existing pattern in `rateLimitKeys`.
3. **Rate limiting is graceful**: If Redis is unavailable, the rate limit check is skipped (returns `null` from `incr`), allowing the vote to proceed. This matches the graceful degradation pattern in `lib/cache/client.ts`.
