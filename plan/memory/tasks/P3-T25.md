## Summary

Created two server-component chat pages: `app/(chat)/page.tsx` (new chat at `/`) and `app/(chat)/chat/[id]/page.tsx` (existing chat at `/chat/[id]`). Both render `ChatStreamProvider → ChatShell` with the appropriate data. The existing chat page uses `'use cache'` + `cacheTag` + `cacheLife('seconds')` for cached data fetching, `notFound()` for access control, and starts a votes promise in parallel for future P6 VoteResolver wiring.

## Files Changed

- `app/(chat)/page.tsx` — created. Server component for new chat route. Gets session, fetches available models + default model in parallel, generates UUID, renders ChatStreamProvider → ChatShell with empty messages, isReadonly=false, visibility="private".
- `app/(chat)/chat/[id]/page.tsx` — created. Server component for existing chat route. Defines `getCachedChat` and `getCachedVotes` with `'use cache'` + `withCache`. Uses `generateMetadata` for dynamic page title. Starts votes promise non-blocking. Awaits chat for access control (notFound if missing or unauthorized). Fetches messages + models in parallel. Converts DB messages to UIMessage[]. Renders ChatStreamProvider → ChatShell with loaded data.

## Deviations

1. **VotesProvider / VoteResolver not wired (deferred to P6)**
   - **Spec said:** Existing chat page renders `ChatStreamProvider > VotesProvider > ChatShell + Suspense > VoteResolver(votesPromise)`.
   - **What was done:** Renders `ChatStreamProvider > ChatShell` with a P6 comment placeholder. The `_votesPromise` is started but unused.
   - **Why:** `VotesProvider` and `VoteResolver` components don't exist yet — they are P6 tasks. The votes promise is started early (non-blocking) per spec to establish the parallel fetch pattern. P6 will wrap ChatShell with VotesProvider and add VoteResolver in Suspense.
   - **Trade-offs:** `_votesPromise` is effectively dead code until P6. Prefixed with underscore and annotated with eslint-disable comment. Minimal cost; establishes the correct data flow shape.

2. **`?q=` / `?query=` auto-submit not implemented**
   - **Spec said:** New chat page reads `?q=` or `?query=` search params and auto-submits via `useChatSession.sendMessage()` with `hasAppendedQuery` guard.
   - **What was done:** Not implemented. The page does not read searchParams.
   - **Why:** Auto-submit requires client-side execution (`useChatSession.sendMessage()` is a client hook). Either ChatShell needs an `initialQuery` prop or a separate client component/hook must be created. Neither exists in the current interface. This is a cross-cutting feature that affects ChatShell's prop contract.
   - **Trade-offs:** Feature gap. Should be addressed in a follow-up task or as part of an integration pass before P3-T27 gate.

3. **StreamBridge not rendered as page sibling**
   - **Spec said (component-wiring.md):** StreamBridge is a sibling of ChatShell at page level.
   - **What was done:** StreamBridge is rendered inside ChatShell (established in P3-T21).
   - **Why:** P3-T21 already rendered StreamBridge inside ChatShell and documented this deviation. This page follows P3-T21's established pattern. See P3-T21 task log for full rationale.
   - **Trade-offs:** None. Consistent with P3-T21 deviation.

## Findings

- **P6 wiring point:** `_votesPromise` in `app/(chat)/chat/[id]/page.tsx` is ready for P6 to unwrap — pass it to VoteResolver inside a Suspense boundary, wrap ChatShell with VotesProvider.
- **`?q=` auto-submit gap:** The spec's success criterion for `?q=` query auto-submit is not met. This requires either: (a) adding an `initialQuery` prop to ChatShell, or (b) creating a client-side `QueryAutoSubmitter` component inside ChatStreamProvider. Should be tracked as a follow-up before P3-T27 gate.
- **Message format conversion:** DB messages are converted to `UIMessage[]` with a simple map (id + role cast + parts cast). The same pattern is used in `app/api/chat/route.ts`. If a shared `convertToUIMessages` utility is created later, both call sites should be updated.
