## Issues

### Issue 1: Route segment config incompatible with cacheComponents
`app/api/health/route.ts` exported `const dynamic = "force-dynamic"` which is explicitly disabled when `nextConfig.cacheComponents` is `true` (per Next.js 16 docs: "The options outlined on this page are disabled if the cacheComponents flag is on"). Build error: "Route segment config 'dynamic' is not compatible with `nextConfig.cacheComponents`. Please remove it."

**Fix:** Removed the export. The route is inherently dynamic (DB queries, cache pings) so no explicit dynamic marking is needed.

### Issue 2: Dynamic API access outside Suspense (5 pages affected)
All pages failed prerendering because layouts called `getAppSession()` (which uses `cookies()`) directly, outside `<Suspense>` boundaries. With `cacheComponents`, dynamic API access must be inside Suspense to enable Partial Prerendering. Affected pages: `/`, `/chat/[id]`, `/login`, `/register`, `/_not-found`.

**Fix:** Restructured all three layouts to wrap dynamic API access in async server components inside `<Suspense>` boundaries. The static shell (html, body, ThemeProvider, etc.) prerenders immediately; session-dependent content streams once cookies resolve at request time.

## Deviations

### Layout restructuring for cacheComponents
**Plan said:** Layouts call `getAppSession()` and `cookies()` directly at the top level (established in P3-T24, P3-T26, P2-T07).
**What was done:** Extracted dynamic API calls into Suspense-wrapped async server components (`SessionShell`, `ChatLayoutShell`, `AuthGuard`).
**Why:** Required for Next.js 16 `cacheComponents` compatibility. With `cacheComponents: true`, dynamic APIs (cookies, headers) must be accessed inside `<Suspense>` boundaries to enable Partial Prerendering. Without this fix, `pnpm build` fails for all pages.
**Trade-offs:** The static shell now shows briefly before session data streams in. In practice this is imperceptible since cookie reads are near-instant. The app's behavior is functionally identical to before — just now compatible with Partial Prerendering.

### Removed route segment config
**Plan said:** P6-T13 established `export const dynamic = "force-dynamic"` for the health route.
**What was done:** Removed the export entirely.
**Why:** Route segment config options are disabled when `cacheComponents: true`. The route is inherently dynamic via database and cache calls — no explicit marking needed.
**Trade-offs:** None. The route continues to be dynamically rendered.

## Findings

### Finding 1: cacheComponents changes rendering model fundamentally
Any future task that adds `cookies()`, `headers()`, or other dynamic APIs to a layout or page MUST wrap them in `<Suspense>` boundaries. Direct top-level access will break the build. This is a permanent constraint with `cacheComponents: true`.

### Finding 2: Build output confirms Partial Prerendering
All pages show `◐ (Partial Prerender)` in build output — static HTML shell with dynamic server-streamed content. API routes show `ƒ (Dynamic)`. Proxy (Middleware) is active. This is the optimal rendering strategy for a chat application.

### Finding 3: loading.tsx files created
Created `app/(chat)/loading.tsx` and `app/(chat)/chat/[id]/loading.tsx` for page-level Suspense fallbacks. These provide loading states while dynamic page content resolves.
