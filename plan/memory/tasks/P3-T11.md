## Deviations

### DEV-1: PendingChats integration via optional callback params instead of direct context access

**Plan said:** "Wires onData callback: chat-title → PendingChats.updateTitle()" and "calls PendingChats.add() before handleSubmit" — implying direct access to PendingChats context.

**What was done:** Added optional callback params `onNewChat` and `onTitleUpdate` to `UseChatSessionParams`. These are called at the appropriate points (new chat creation, chat-title stream part) but are no-ops when not provided.

**Why:** PendingChatsProvider (P5-T02) does not exist yet. Using optional callbacks follows the dependency injection pattern — ChatShell (P3-T21) will wire these to `usePendingChats()` when the provider is created. This keeps the hook decoupled from a context that doesn't exist and is independently testable.

### DEV-2: No `maxSteps: 5` in useChat config

**Plan said:** "Calls useChat with... maxSteps: 5"

**What was done:** Omitted `maxSteps` from useChat configuration.

**Why:** `maxSteps` is not a valid `ChatInit` option in the current AI SDK v5. Tool call looping (multi-step) is handled server-side via `streamText`'s `maxSteps` parameter (P3-T23). The client-side equivalent (`sendAutomaticallyWhen`) is for client-side tool execution, which we don't use — our tools run server-side.

### DEV-3: SDK data part wire format transformation

**Plan said:** "onData routes artifact-* parts to useChatStreamDispatch"

**What was done:** The `onData` callback transforms SDK wire format (`{ type: 'data-artifact-id', data: unknown }`) to our internal `DataPart` format (`{ type: 'artifact-id', content: string }`) before pushing to ChatStreamDispatch. The SDK prefixes all data parts with `data-` and uses `data` field instead of `content`.

**Why:** This is how the AI SDK v5 delivers custom data parts. The transformation is necessary and correct — our internal `DataPart` type was designed for the domain layer, not SDK wire format.

### DEV-4: File length ~215 lines vs ~120 target

**Plan said:** "~120 lines"

**What was done:** 215 total lines (130 hook body).

**Why:** The ~120 estimate didn't account for: params interface definition (18 lines), adaptive throttle utility (8 lines), import section (18 lines), refs for stale-closure safety (8 lines), and SDK wire-format transformation in onData (6 extra lines). The hook body itself is ~130 lines. The old Chat component was 524 lines — this is a 75% reduction while being fully typed and more maintainable. Still not a God Component.

## Findings

### FND-1: AI SDK v5 data part wire format uses `data-` prefix

The AI SDK v5 `onData` callback receives data parts in format `{ type: 'data-<name>', data: unknown, id?: string }`, NOT the raw `{ type: '<name>', content: '<value>' }` format. The server's `createUIMessageStream` writer must send parts as `writer.write({ type: 'data-artifact-id', data: 'uuid' })`. **This affects P3-T23 (chat API route)** — the route handler must use the SDK's `data-` prefixed types when writing to the stream.

### FND-2: AI SDK v5 useChat no longer provides input/setInput/handleSubmit/attachments

The new `useChat` from `@ai-sdk/react` returns only: `id`, `messages`, `setMessages`, `sendMessage`, `regenerate`, `stop`, `resumeStream`, `addToolResult`, `status`, `error`, `clearError`. Input management (`input`, `setInput`), attachment management, and form submission are now the consumer's responsibility. Our hook manages these as local state.

### FND-3: `stop()` returns `Promise<void>` in SDK vs `void` in ChatSessionValue

The SDK's `AbstractChat.stop` returns `Promise<void>` while our `ChatSessionValue.stop` type is `() => void`. This is compatible in TypeScript (void return type ignores the actual return value), so no code change is needed. Noted for awareness.

### Notes (Non-Blocking)

1. **`editMessage` ignores `ActionResult` from `deleteTrailingMessages`:** The server action returns `ActionResult<void>` but the hook doesn't check `result.success`. If the server-side delete fails (auth, DB error), the resubmit still fires, potentially creating inconsistent state. This is a **robustness concern** — not blocking for this task, but should be addressed when message editing is wired end-to-end (P3-T16/P3-T21).

2. **`as DataPart` type assertion in `onData`:** `{ type: sdkType.slice(5), content: dataPart.data } as DataPart` — the guard `sdkType.startsWith("data-artifact-")` ensures only valid artifact types pass through, but the assertion bypasses compile-time narrowing. Acceptable since we control both server writer and client consumer.

3. **Line count:** Task log says "~215 lines total" — verified at exactly **215 lines** via `(Get-Content ...).Count`. Task log was accurate.

4. **P3-T09 callback factories unused (undocumented deviation):** The spec explicitly lists `features/chat/lib/chat-callbacks.ts (P3-T09)` as an input, with the description: *"These callbacks are injected into useChatSession rather than being inline, making the orchestrator testable."* The implementation inlines all callbacks instead, completely ignoring the factory functions. This is acceptable (SDK v5 changes invalidate some of the factory patterns), but it should have been documented as DEV-5. The `chat-callbacks.ts` file may become dead code if no other consumer uses it.
