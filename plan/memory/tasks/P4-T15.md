## Summary

Created `app/api/artifact/route.ts` with GET and POST handlers for the artifact API. GET returns all artifact versions by id with auth + ownership checks. POST supports two modes via discriminated union: `save` (persists new version + revalidates cache) and `restore` (truncates later versions + revalidates cache). All inputs validated via Zod, all operations auth-gated, errors handled via `AppError.toResponse()`.

## Deviations

**1. POST body contains `id` instead of query param `?id=`**

- **Plan said:** Old app uses `?id=` query param for POST (and spec mentions `POST /api/artifact?id=`).
- **What was done:** Both save and restore modes include `id` (artifactId) in the POST body, validated by Zod discriminated union.
- **Why:** Since the POST endpoint uses a discriminated union on `mode`, having `id` in the body keeps all inputs colocated and validated as a single unit. The old app's separate GET param `?id=` + body approach splits validation and is harder to type-check. Both modes already need `id`, so body inclusion is cleaner.
- **Trade-offs:** Consumers must include `id` in the body instead of as a query param. Minimal impact since the artifact panel and AI tools construct the full request body.

**2. Local Zod schemas instead of importing from `features/artifacts/schemas/artifact.schema.ts`**

- **Plan said:** Inputs from `features/artifacts/schemas/artifact.schema.ts` (P4-T01).
- **What was done:** Defined route-specific Zod schemas locally in the route file for the POST body discriminated union. The existing feature schemas (`getArtifactSchema`, `deleteArtifactVersionSchema`) are designed for different shapes (no `mode` field, no `content`/`title`/`kind` in delete schema).
- **Why:** The API route needs a discriminated union schema combining save and restore modes with different field sets. Reusing feature schemas would require awkward composition (`.extend()` + `.merge()`) that's harder to read than simple local definitions. Route handlers commonly define their own request validation schemas per `patterns.md` § 3.
- **Trade-offs:** Minor duplication of UUID validation logic; acceptable given the different structural requirements.
