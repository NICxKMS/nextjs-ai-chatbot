## Deviations

1. **Logout mechanism**: The old app used `fetch("/api/auth/logout", { method: "POST" })` + `getSupabaseBrowserClient().auth.signOut()` + SWR cache clearing + `router.push("/")`. The new implementation calls the `logout()` server action directly (from `features/auth/actions/logout.ts`), which handles server-side Supabase sign-out, guest cookie clearing, and `redirect("/login")` in one atomic operation. This is simpler, more secure (no client-side API endpoint needed), and follows the new architecture's "Server Actions only for mutations" rule.

2. **Auth hook**: Old app used `useAuth()` from a custom `auth-provider`. New implementation uses `useSession()` from `features/auth/components/session-provider.tsx`, which exposes `{ session, isLoading, isGuest }` — cleaner API with explicit `isGuest` boolean instead of manually checking `session?.user?.type`.

3. **Login link**: Old app used `router.push("/login")` via a button `onClick`. New implementation uses a `<Link href="/login">` inside `DropdownMenuItem asChild`, which is more semantic (proper anchor tag) and supports browser features like middle-click and right-click open-in-new-tab.

4. **Transition state**: Added `useTransition` for the sign-out action to show "Signing out…" text during the server action, providing better UX feedback. The old app had no pending state indicator for logout.

### ⚠️ Notes

**`redirect()` + `try/catch` interaction (lines 116–123):**

The `logout()` server action ends with `redirect("/login")`. On the client, `await logout()` is wrapped in `try/catch` inside `startTransition`. Per the Next.js 16 docs (`.next-docs/01-app/03-api-reference/04-functions/redirect.mdx`):

> "redirect throws an error so it should be called outside the try block when using try/catch statements"

When a server action calls `redirect()`, it sends a 303 response. On the client, Next.js handles the redirect and triggers navigation. Whether the `await` also throws `NEXT_REDIRECT` on the client depends on internal framework behavior. **If** it does throw, `toast.error("Failed to sign out, please try again.")` would fire briefly before the page navigates away — a minor UX flash rather than a functional break.

**Risk:** Low. The redirect navigation will occur regardless. The worst case is a brief, possibly imperceptible toast flash before the /login page loads. Idiomatic fix would be using `unstable_rethrow(error)` in the catch block or checking for redirect errors, but this is a refinement, not a blocker.

**Recommendation:** Log as a follow-up item for when server action + redirect patterns are stabilized across the codebase. Not blocking P5-T06.
